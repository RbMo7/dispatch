# Chain is a renamed, fully-qualified family+tier identifier — not an additive value, not a separate environment column

Every registered chain until now has secretly been a testnet: `Chain` was `"base" | "solana"`, but the only registered executors pointed at Base Sepolia and Solana Devnet. Going live on mainnet meant introducing a real "which network" axis, and there were two shapes on the table: an orthogonal `network` (`TESTNET`/`MAINNET`) field threaded through `Payment`/`Dispatch`/`TenantWallet` alongside the existing `chain`, or folding tier straight into `Chain` itself. Both were prototyped in discussion before this ADR; folding it into `Chain` won.

**`Chain` becomes `"base-sepolia" | "base-mainnet" | "solana-devnet" | "solana-mainnet"`.** This is a rename, not an addition — `"base"` and `"solana"` do not survive alongside the new values. Every existing row in every chain-keyed column (`tenant_wallets`, `payments`, `execution_plans`, `transactions`, `claim_wallets`) is migrated to its Sepolia/Devnet equivalent, since all of today's data already is testnet data. A caller naming the old bare values gets a validation error, not a silent default — there is no backward-compatible shim.

**Sandbox and Live are a derived label, never a stored column.** Whether a Chain value is Sandbox or Live is answered by checking its suffix (`-mainnet` = Live, everything else = Sandbox) at the point something needs to know — the Wallets screen's grouping, the Dispatch intake tier-mixing check (see below). No table gained an `environment`/`network`/`tier` column. This was chosen over the orthogonal-column shape specifically because `ChainExecutor` was already, in practice, one instance per network (Base Sepolia's executor already differs from a hypothetical Base Mainnet one in RPC URL, chain ID, and USDC address, not just in "chain") — the registry's own extension comment ("implement `ChainExecutor` in its own file, then register it here — nothing else should need to change") already assumed one Chain value per registered network, so making that literal cost less than introducing and threading a second dimension through five tables.

**One API Key spans both tiers.** There is no test/live key split (unlike, say, Stripe's `sk_test_`/`sk_live_` pattern). A Tenant's single API Key can submit a Dispatch naming either a Sandbox or a Live Chain value, gated only by whether that Tenant has actually provisioned the corresponding wallet (ADR pending on mainnet wallet provisioning). This is a deliberate, named tradeoff, not an oversight: a leaked API Key is exactly as dangerous against a Tenant's Live wallets as its Sandbox ones once that Tenant has gone live. Building real key-level environment scoping is the trigger condition for eventually building the fuller Stripe-style dual-key architecture this ADR explicitly does not build.

**A single Dispatch may never mix tiers.** Intake validation derives each Payment's tier from its Chain value and rejects the whole Dispatch if any two Payments disagree — there's no sane case for moving real and fake money in one idempotent batch. Mixing chain *families* at the same tier (a `solana-mainnet` payment alongside a `base-mainnet` one) is unaffected.

**Consequence**: every existing reference to bare `"base"`/`"solana"` — in code, tests, Bruno collections, and prior ADRs (0006, 0007, 0008) — needs updating or an explanatory pointer forward to this one. `api_keys`' `dsp_live_` secret prefix predates this ADR and is unrelated naming (a generic "this is a real key" prefix, not a Live-tier marker) — it is not renamed by this decision.
