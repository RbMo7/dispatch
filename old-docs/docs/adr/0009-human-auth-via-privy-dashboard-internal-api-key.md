# Human auth via Privy, bridged to the API by a dashboard-internal API Key

Status: superseded by ADR-0014 for the human-auth half — dashboard login is email+password now, Privy is Tenant Wallet custody only. The dashboard-internal API Key / session-cookie bridge this ADR establishes is unchanged; only how the human is verified changed.

Every credential in the system so far has been machine-to-machine: an API Key, shown once, meant to live in a backend. The Tenant Dashboard needs a human to return tomorrow and see the same Tenant's Dispatches, which means a login. `03-sign-in-and-auth.md` named the gap and proposed a direction without committing to endpoint shapes; this ADR commits to them.

**Auth vendor**: Privy, not a second identity vendor. `@privy-io/node` is already a dependency (`signing/privyProvider.ts`, ADR-0008) for Tenant Wallet custody, and Privy's core product is authentication (email OTP, wallet-connect) with embedded wallets on top. One Privy application is now used for two products: server-side wallet custody (existing `PRIVY_APP_ID`/`PRIVY_APP_SECRET`) and human sign-in (the same `PRIVY_APP_ID` exposed publicly as `NEXT_PUBLIC_PRIVY_APP_ID`, verified server-side with the same `PRIVY_APP_SECRET`). Email OTP is the only path built for v1; wallet-connect is a plain secondary link, not a competing button.

**Signup and sign-in are one flow.** The anonymous `POST /v1/tenants` endpoint is kept, not removed. It's a working, rate-limited endpoint API integrators may already script against, and the sign-in doc's "unify, don't build a second flow" was about the landing page having one entry point, not about deleting that path. A human's first sign-in provisions a Tenant through the same wallet-provisioning + Tenant-creation transaction `POST /v1/tenants` already runs, just entered from a verified identity instead of an anonymous call.

**One identity per Tenant**: `tenants.privy_user_id` (unique, nullable — nullable because Tenants created via the anonymous path have none). No team/multi-member accounts, no roles, no invites, matching the same flat-column-not-a-permissions-table discipline ADR-0008 already applied to `payments.tenant_id`.

**The session-to-API bridge**: a human's browser never holds a Tenant's real API Key. A signed-in dashboard session carries a **dashboard-internal API Key** instead — stored and checked exactly like any other row in `api_keys` (same `key_hash` column, same `requireApiKey` preHandler, zero changes to that function), distinguished only by a new `api_keys.is_internal` boolean. That flag excludes it from `GET /v1/tenants/me`'s `api_keys` list and from the revoke-lockout count, and a revoke request naming its id 404s exactly like a different Tenant's key would. Its plaintext secret is captured once, at mint time, and never persisted server-side: it goes straight into an encrypted, httpOnly, `sameSite=lax` session cookie (alongside `tenant_id`) that only the Next.js server decrypts. A fresh internal key is minted on every sign-in rather than reused, so there's never a moment a decryptable copy needs to live in Postgres. This is the same "shown once" discipline that already governs user-facing keys, with no carve-out for this one.

**New internal endpoint**: `POST /internal/dashboard-session`, guarded by a shared-secret header (`X-Internal-Secret` against `INTERNAL_API_SECRET`, held by both `api` and `web`), registered in its own Fastify scope with no other preHandler. Not `requireApiKey`, and not reachable from a browser, only server-to-server from the Next.js app. Resolves an existing Tenant by `privy_user_id` (revoking any prior internal key first) or provisions a new one, in both cases returning a freshly-minted internal key. Concurrent first-time calls with the same `privy_user_id` resolve to one Tenant via the unique constraint, the same insert-then-read-existing-on-conflict pattern already proven for `dispatches.idempotency_key`.

**Consequence**: `api_keys` now holds two kinds of row distinguished by one boolean instead of two tables, which is deliberate (see the flat-column reasoning above) but means every future query against `api_keys` that assumes "a row here is a Tenant-visible key" needs to filter `is_internal = false` explicitly, the way this change already does in the two places that mattered (`GET /v1/tenants/me`, the revoke lockout check).

**Does not contradict ADR-0008.** It's additive: ADR-0008 established Tenants, API Keys, and per-Tenant wallets with no concept of a human identity; this ADR adds that identity and a second, internal-use kind of API Key on top of the same tables, without changing how `requireApiKey`, `tenant_wallets`, or the existing anonymous signup path work.
