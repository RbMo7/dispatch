# Real Solana USDC support; a getBalance failure can no longer crash a Coordinator tick

`SUPPORTED_ASSETS_BY_CHAIN` (`validation/dispatch.ts`) has always listed USDC as valid on `solana-devnet`/`solana-mainnet`. The Solana `ChainExecutor` never actually implemented it — `prepare()` threw for any asset but SOL, and `getBalance()` did the same. This drifted silently because no existing test ever submitted a real Solana USDC Payment through the funding-check path; every prior test used SOL or Base USDC. It surfaced live, in a real demo run: a chain-less Payment routed to `solana-devnet` for USDC, `findShortfalls` called `getBalance(address, "USDC")`, it threw, and the throw propagated uncaught out of `processChainGroup` and out of `runCoordinatorTick`'s per-group loop entirely — aborting the tick before either payment in that batch (one of them on an unrelated chain) got past its initial `QUEUED → PROCESSING` claim. A `PROCESSING` row is never reclaimed by a later tick, so both payments were stuck permanently, with no retry path (manual retry only works on `FAILED`).

**Two fixes, found and shipped together:**

**1. Real SPL/USDC support in the Solana executor** (`chains/solana/executor.ts`). `getBalance` now derives the Associated Token Account via `getAssociatedTokenAddress` and reads it with `getAccount` — a `TokenAccountNotFoundError` (no ATA yet, i.e. this address has never held USDC) is a real `"0"`, not a throw. `prepare()` now builds real SPL instructions per Payment: `createAssociatedTokenAccountIdempotentInstruction` (idempotent — costs nothing extra if the recipient's ATA already exists) followed by `createTransferCheckedInstruction`, alongside the existing native-SOL `SystemProgram.transfer` path in the same batched transaction. The USDC mint is config (`SOLANA_DEVNET_USDC_MINT`/`SOLANA_MAINNET_USDC_MINT`, defaulting to Circle's published devnet/mainnet mints — see `.env.example`), mirroring how the EVM executor already takes its USDC contract address as config.

**2. `findShortfalls` no longer lets one bad `getBalance` call crash the whole tick.** The per-asset `getBalance` call inside `findShortfalls` (`coordinator/fundingCheck.ts`) is now wrapped in a try/catch — a failure is treated as a full shortfall (balance `0`) rather than propagating. This is deliberately generic, not a Solana-USDC-specific patch: any future asset/chain combination the validation layer accepts but an executor doesn't actually implement will now fail that one candidate cleanly (`insufficient_funds` or, for the Decision Engine, a rejected Route Candidate) instead of silently bricking every payment claimed in that tick. Correct either way — a balance that can't be confirmed can't be spent — but the failure mode changes from "the whole system quietly stops making progress" to "this one payment fails loudly."

**Consequence**: `SUPPORTED_ASSETS_BY_CHAIN` and what a Chain Executor actually implements are still two separate pieces of code that can drift again for a future asset. The crash-guard means that drift now fails safely; it doesn't mean the drift can't happen. Adding a new asset to that table still requires actually implementing it in every listed chain's executor — this ADR doesn't change that discipline, it just makes forgetting to non-fatal.
