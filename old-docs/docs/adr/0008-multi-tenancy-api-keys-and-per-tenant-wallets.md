# Multi-tenancy: Tenants, API Keys, and per-Tenant wallets replace the single global sender

Dispatch was single-tenant: one global sender address per chain from env vars, and no authentication at all on `POST /v1/dispatch`. `CONTEXT.md` already named Tenant and API Key as the target vocabulary; this ships it. New tables — `tenants`, `api_keys` (hashed, a Tenant may hold several active keys, each independently revocable), and `tenant_wallets` (one Privy-custodied wallet per Tenant per chain) — plus `tenant_id` on `dispatches` and `payments`. Every dispatch route now requires a `Bearer` API key. Idempotency Keys became unique per Tenant instead of globally: the old constraint would have silently handed Tenant B Tenant A's dispatch had they ever picked the same key string.

**Custody**: one Privy org, one wallet minted per (Tenant, chain), not Turnkey sub-organizations — no per-tenant signing-provider choice, Privy only for new Tenant Wallets. This reuses `PrivyProvider`'s existing `register(address, walletId)` map exactly as ADR-0006 designed it: adding per-tenant wallets required one new `createWallet` method on `PrivyProvider`, no interface changes. `ChainExecutor.prepare`/`sign` now take an explicit `sender` instead of reading a global env var, and the Coordinator resolves each tenant's wallet before signing. The pre-existing global sender addresses (real, funded, still in `.env`) were preserved by seeding a fixed-id "Demo Tenant" (migration 0005) rather than breaking everything already relying on them.

**Signup**: self-serve. `POST /v1/tenants` is public, provisions both chains' wallets via a real Privy call *before* writing anything to the database — a Privy failure leaves nothing half-created — and returns the first API Key once.

**Security hardening applied in this pass** (found via a source-first security review, not designed in up front): a self-serve, unauthenticated signup endpoint that also accepts a server-fetched `webhook_url` is a stock combination of two problems, both fixed here rather than deferred:
- *Resource exhaustion*: each signup call drives two billable Privy calls and four DB row inserts with zero gating. `POST /v1/tenants` is now rate-limited (5 per 15 minutes per IP, via `@fastify/rate-limit` scoped to just that route). This is not a substitute for CAPTCHA or email verification — neither exists yet — just a floor.
- *SSRF*: a Tenant's `webhook_url` is fetched server-side by `sendPendingWebhooks` on every delivery attempt, and delivery status is visible back through `GET /v1/dispatch/:id` — an anonymous signup could otherwise point it at an internal host (including the cloud metadata address) and use delivery status as a response-code oracle for internal reconnaissance. `webhooks/urlSafety.ts` re-validates scheme and resolves+rejects private/loopback/link-local ranges immediately before *every* delivery attempt (not just once at signup), and delivery no longer follows redirects. This check only applies to a Tenant-supplied URL — the operator-configured internal-sink default is exempt, since it's trusted config, not attacker input. A narrow DNS-rebinding window between the resolve and the `fetch()` call right after it remains; closing that fully means pinning the resolved address through the actual TCP connection, deferred as a known residual gap.

Consequence: production use of self-serve signup should add real abuse controls (CAPTCHA/email verification, tighter or IP-aware rate limiting) before it's public-facing for real — the rate limit here is a floor, not a complete answer. If the residual DNS-rebinding gap in webhook delivery ever matters, the fix is a custom fetch dispatcher that pins the resolved address through the connection, not a re-review of this pass's approach.

Note (ADR-0010): per-Tenant wallets are provisioned per Chain, and Chain has since been renamed to a fully-qualified family+tier identifier (`base-sepolia`, `base-mainnet`, `solana-devnet`, `solana-mainnet`) — this ADR's "one wallet per (Tenant, chain)" invariant is unchanged, it now just spans four registered chains instead of two, with the two Live ones opt-in rather than provisioned at signup.
