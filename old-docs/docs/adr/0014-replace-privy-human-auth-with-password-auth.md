# Dashboard login is now email+password; Privy is wallet custody only

Status: supersedes ADR-0009's human-auth half

ADR-0009 used one Privy application for two unrelated products: Tenant Wallet custody (ADR-0008) and human sign-in to the dashboard. In practice that coupling showed up directly as a Dispatch product problem: creating two independent demo Tenants (an NGO disbursement integration and a payroll integration) each needing their own dashboard access required two separate Privy identities, and Privy only allows one email-type account per identity — so a second sign-in attempt in the same browser session surfaced as `cannot_link_more_of_type` instead of just creating a second account. There's no actual reason dashboard login needs to be tied to the same identity system as wallet signing; the coupling was incidental (one Privy app was already a dependency for wallets, ADR-0006/0008), not load-bearing.

**Dashboard login is now a plain `email` + `password_hash` pair on `tenants`**, replacing `privy_user_id`. Password hashing is `node:crypto`'s built-in `scrypt`, salted per password (`auth/passwordAuth.ts`) — no new dependency, and deliberately a slower/salted hash than API Keys' plain sha256 (`auth/apiKeyAuth.ts`), since a password is human-typed and human-reused across services in a way a generated bearer secret never is.

**Two ways to end up with a login**: sign up through the dashboard (`POST /internal/dashboard-session` with `mode: "signup"` — name+email+password, provisions a new Tenant + wallets exactly as `provisionTenant` always has) or add one after the fact to a Tenant that already exists from the anonymous `POST /v1/tenants` path (`POST /v1/tenants/me/set-password`, authenticated with the Tenant's own API Key). A Tenant may have an API Key with no login, a login with no separately-copied API Key, or both — they're independent credentials for independent purposes, not a hierarchy.

**Signup no longer resolves an existing identity — an already-used email is a 409.** Privy's flow could safely treat a repeat `privy_user_id` as "the same verified person, resolve to their Tenant" because Privy had already verified the identity. Nothing here verifies an email up front (no confirmation link, no OTP), so a repeat email during signup can't be trusted to be the same person — it's a straightforward conflict, and the caller is told to log in instead.

**Login is a single generic failure** (`401 Invalid email or password`) whether the email doesn't exist, has no password set yet (an anonymous, API-key-only Tenant that never called `set-password`), or the password is wrong — the same information-leak discipline any password login needs, just newly relevant here since nothing before this needed it.

**Not done**: password reset/forgot-password (no email delivery exists anywhere in this codebase to build it on), rate limiting on the login path specifically (the existing signup rate limit on `POST /v1/tenants` doesn't cover `/internal/dashboard-session`), and migrating any previously-Privy-signed-in Tenant's data — there were none to migrate at the time of this change. Both the web app's `@privy-io/react-auth` dependency and `PRIVY_APP_ID`-as-public-auth-config are gone from `web/`; the API's own `PrivyProvider` (wallet custody, `signing/privyProvider.ts`) is untouched.
