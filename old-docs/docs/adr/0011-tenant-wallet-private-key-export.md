# Tenant Wallet private key export

Every Tenant Wallet is Signing-Provider-custodied (Privy) — Dispatch's engine never holds a raw private key itself, but until now neither did the Tenant. A Tenant who wanted to move funds through a wallet Dispatch executes from had exactly one option: ask Dispatch to do it. That's a real lock-in, at odds with Dispatch's own stated purpose as adoptable execution infrastructure rather than a custodian.

**Any Tenant Wallet, any tier, can have its raw private key exported**, via the Signing Provider's export capability. The wallet is app-owned (created with no separate Privy-user ownership), so the same app credentials that create and sign for it today authorize the export — no new authorization scheme, no per-wallet owner key to manage. Available uniformly on Sandbox and Live wallets; restricting it to Live only would add complexity (a chain-tier check gating a chain-agnostic mechanism) for no real safety benefit, and letting a Tenant rehearse the export flow risk-free on a Sandbox wallet before ever touching a Live one is a genuine benefit of not restricting it.

**One-time reveal, gated by a re-typed confirmation, not re-authentication.** The plaintext key is captured once, held only long enough to hand back to the requesting Tenant's already-authenticated dashboard session, and never persisted anywhere — the same "shown once" discipline ADR-0009 already established for API Key secrets. The confirmation step is stricter than that precedent, though: revoking an API Key is trivially reversible (create another one); exporting a private key is not. A plain "click confirm" pattern was rejected in favor of requiring the Tenant to type a confirmation phrase before the key is ever requested from the Signing Provider. Re-authenticating the dashboard session itself (e.g. a fresh Privy OTP) was considered and rejected — the session is already a live, short-lived, Privy-backed credential, and a second auth step adds friction without meaningfully raising the bar for someone who has already compromised that session.

**No backend throttle on repeat exports.** A Tenant can export the same wallet's key more than once; the friction lives entirely in the dashboard's confirmation step, not as a server-side lockout. It's the Tenant's own wallet — restricting how often they can look at their own key has no threat model behind it once the confirmation gate exists.

**Consequence, and the reason this needed an ADR at all: after an export, Dispatch's own signer can no longer be assumed the sole controller of that wallet.** The Tenant could move funds through the exported key independently and invisibly to Dispatch — a live Dispatch could still queue and attempt to execute Payments from that wallet, and would simply see whatever balance is actually there, same as it does today for any other reason a wallet might be short. Every export is logged (wallet, tenant, timestamp) precisely because this is the one action in the system that changes who's really in control of a wallet going forward, and that fact needs to be discoverable after the fact, not just in the moment.

**One real deviation from this ADR's original assumption, discovered live**: "authorized by this app's own credentials, no per-wallet owner needed" turned out to be wrong — Privy's export API rejects an export outright on a wallet with no `owner` at all (`401: "A wallet must have an owner to perform this action"`), regardless of which app credentials call it. Every Tenant Wallet is created ownerless (ADR-0008/0010: app-controlled, no per-tenant Privy user). The fix: a single P-256 keypair (`generateP256KeyPair()`, not a Privy user) that this app holds and sets as the `owner` on every wallet going forward, with its private key passed as `authorization_context` on each export call. A wallet created before this keypair existed has no owner yet — rather than a one-off backfill migration, `PrivyProvider.exportPrivateKey` catches that specific 401, calls `wallets().update()` to set the owner, and retries once. A second discovery: the exported private key's format is chain-native and undocumented in the SDK's types — bare hex with no `0x` prefix for an EVM wallet, base58 for Solana — confirmed by inspecting a real export, not by reading a spec.
