# Decision Engine: an optional pre-Coordinator routing step for Chain-less Payments

Until now every Payment named its Chain explicitly — the caller decided where money moved, and Dispatch only handled how. That's a real ceiling on the "client doesn't need to understand any single chain's execution model" promise in this repo's own framing (`CONTEXT.md`'s opening line): a caller who doesn't care which chain Alice gets paid on, only that she gets paid cheaply, still has to pick one today. The Decision Engine removes that requirement for callers who want it, without touching the existing explicit-Chain path at all.

**Chain becomes optional per Payment, additively.** A Payment with `chain` given behaves exactly as today — the Decision Engine never runs for it. A Payment with `chain` omitted must instead carry Recipient Addresses (one candidate address per Chain), and the Decision Engine resolves a concrete Chain for it before the Execution Coordinator ever sees it. Zero regression risk to the existing, tested explicit-Chain path; no request shape was broken, only extended.

**Resolution happens once per Payment, inside the existing QUEUED→PROCESSING claim — never on the `POST /v1/dispatch` ingest path, and no new visible Payment Status.** Same structural non-negotiable ADR-0012 already established for the funding check: a synchronous chain RPC call at ingest time would mean paying that cost on every Dispatch submission regardless of whether routing is even used. A Chain-less Payment is claimed like any other, routed, and falls straight into the same `(Tenant, Chain)` grouping as an explicit-Chain Payment — no `ROUTING` status was added; resolution is fast enough to be invisible as a separate stage. No viable Route Candidate fails the Payment with reason `no_viable_route`, the same pattern as the existing `invalid_recipient`/`insufficient_funds` reasons on `FAILED`.

**A Routing Decision is its own persisted entity, not folded into Execution Plan.** An Execution Plan already means something specific and chain-fixed (a Chain Executor's batching unit, ADR-0002's "bridge between the payment-level view and the transaction-level view"). Reusing that name or that table for a pre-chain-selection decision would have collided two genuinely different concepts under one name. A Routing Decision instead records every Route Candidate the Decision Engine considered for a Payment — viable or rejected, and why — plus the Chain chosen and the Execution Preference that drove it. Storing only the winner was rejected: the comparison itself (e.g. "Solana $0.02 vs Base $0.18, chose Solana") is the entire point of making routing visible rather than a black box, so throwing it away after the decision would undercut the one thing this feature is for.

**Candidate filtering reuses ADR-0012's liquidity check and the existing `SUPPORTED_ASSETS_BY_CHAIN` table directly — no parallel logic was built.** A Route Candidate is viable only if: a Recipient Address was supplied for that Chain, the Payment's asset is in `SUPPORTED_ASSETS_BY_CHAIN` for it, and `findShortfalls` (ADR-0012) shows the Tenant's wallet can afford it. All three checks already existed for other purposes; the Decision Engine calls them per candidate instead of building a second implementation of "can this Tenant afford this Chain."

**Cost ranking uses a static, config-seeded cost table, not a live per-request fee query.** This mirrors `fundingCheck.ts`'s existing `GAS_RESERVE_PER_PAYMENT` pattern of treating fees as pre-decision approximations rather than live-critical values, and is a deliberate choice, not a shortcut: on the sandbox chains this demo runs on, live testnet fees are near-zero and don't track real market pressure, so a live query would produce noise ("$0.00 vs $0.00") instead of the cost contrast the feature exists to show. Real fees remain computed exactly as before, by the Chain Executor's own `prepare()`, at actual broadcast time — the static table is only ever used for ranking Route Candidates, never for sizing a transaction.

**Execution Preference is scoped per-Payment, not per-Tenant.** The plan this was designed from called these "tenant preferences," but that would have collided with the account-level convention ADR-0012 already established for Funding Mode (`_Avoid_: per-Dispatch or per-Payment funding settings` — CONTEXT.md). A routing preference has no equivalent reason to be account-wide: a single Dispatch can freely mix an explicit-Chain Payment, a `cheapest`-routed one, and an `allowed_chains`-restricted one. Of the five preferences the source plan named, only `cheapest` (default) and `allowed_chains` (a pre-ranking filter, not a ranking rule) are implemented; `fastest`, `balanced`, and `max_execution_fee` are named in `CONTEXT.md` but not built — no per-Chain speed or reliability signal exists yet to rank by.

**A new `payment.routed` webhook event fires when a Routing Decision is made**, following the same lifecycle-event pattern as `payment.broadcasted`/`payment.confirmed`/`payment.failed` — no new event *kind* of concept, just one more transition on the existing outbox pipeline.

## Consequences

- Any endpoint or dashboard view that lists a Payment's Chain now needs to handle it being genuinely unset until a Routing Decision resolves it (mid-tick, effectively instantaneous, but not guaranteed synchronous with the `POST /v1/dispatch` response the way an explicit-Chain Payment's Chain is).
- The static cost table is a demo-scoped approximation, not a production fee oracle — anyone wiring a real `fastest`/`balanced`/`max_execution_fee` preference later will need a real per-Chain speed/reliability signal that doesn't exist yet, not just an extension of this table.
- Recipient Addresses are supplied by the Tenant, not discovered by Dispatch. A general recipient-identity/address-book capability (resolving "which Chains can this Recipient receive on" on Dispatch's own initiative) remains explicitly out of scope.
