# Prefunded and Reactive funding modes; webhook_outbox gains a wallet-scoped event

Dispatch is pure execution infrastructure — no policy, no compliance layer, no opinion on how a Tenant manages treasury. Until now, that also meant no opinion on funding: a Payment against an underfunded wallet simply failed once a broadcast attempt hit it, discovered the hard way with a generic error, and nothing about the flow gave a Tenant's own automation a way to react ahead of time. That's a real gap in the "no vendor lock-in" story this engine is meant to tell: a Tenant should be able to wire their own treasury automation to Dispatch's signal, not be forced to either babysit balances manually or build their own separate polling layer against `GET /v1/dispatch`.

**A Tenant picks one of two funding modes, once, at the account level** (`tenants`, alongside `webhook_url`) — not per-Dispatch, not per-Payment. There's no case for a single Tenant wanting both "fail fast" and "wait and notify" behavior for different batches, so a per-request override was rejected as unneeded surface area.

- **Prefunded** (the default — no existing Tenant's behavior changes): the Tenant is expected to keep wallets loaded ahead of time. A shortfall fails the affected Payments immediately, now with a clean `insufficient_funds` reason instead of discovering it only via a failed broadcast.
- **Reactive**: the Tenant doesn't pre-load anything. A shortfall pauses the affected Payments in a new `AWAITING_FUNDS` status and fires a webhook naming exactly what's needed; once the wallet is topped up, they resume automatically on the next Coordinator tick.

**The check runs at Coordinator-tick time, for every (Tenant, Chain) group, before an Execution Plan is formed — never on the `POST /v1/dispatch` ingest path.** This was the one structural non-negotiable: `dispatch.ts`'s service layer does pure DB writes today, with all chain-awareness living in the Coordinator (ADR-0003). Adding a synchronous balance check at ingest time would have meant a chain RPC call on every Dispatch submission regardless of funding mode; keeping the check where the Coordinator already reads chain state means both modes are just two outcomes of one check, at one place, and "list of every Dispatch" naturally falls out of the Coordinator's existing per-tick grouping across all of a Tenant's pending Dispatches for a chain — nothing new had to be built to look at more than the just-submitted Dispatch.

**`AWAITING_FUNDS` is a first-class Payment status, not an overload of `QUEUED`.** `CONTEXT.md`'s existing Payment Status entry is deliberately precise (it already calls out that `FAILED` isn't a dead end and that there's no separate "retrying" status); silently reusing `QUEUED` to sometimes mean "blocked on your balance" would have undercut that precision and left a Tenant's dashboard with nothing to show beyond "still queued, for some reason."

**`webhook_outbox.dispatch_id` becomes nullable, and the table gains a `tenant_id` column** — the first webhook event type that isn't naturally scoped to one Dispatch. A shortfall is a property of a (Tenant, Chain) group, which can span many Dispatches at once; forcing it onto one arbitrarily-chosen Dispatch would have been dishonest about what the event is actually about, and a second, parallel outbox table would have duplicated the entire retry/backoff/delivery pipeline for one event type. The existing delivery pipeline (`sender.ts`) is extended to resolve a row's target URL via `tenant_id` directly when `dispatch_id` is null, otherwise unchanged.

**The webhook payload is a per-asset shortfall array, not one combined figure**, because an EVM group can be short on its payment asset and its native gas independently — a single number would be ambiguous on any chain where the payment asset isn't also the gas asset. Each entry is the exact top-up amount still needed (required minus current balance), not the wallet's full required balance, so a listening integration can act on it directly without a separate balance lookup of its own. Firing is debounced to once per shortfall "episode" per (Tenant, Chain) — an unchanged gap doesn't re-fire, a growing one does — with a symmetric resolution event once the group actually executes, so an integration can log "was blocked, now resolved" without polling.

**Consequence**: any future query against `webhook_outbox` that assumes every row has a `dispatch_id` needs to handle the null case, the same way ADR-0009 already flagged for `api_keys.is_internal`.
