# `base` and Ethereum L1 are separate Chain identities, not one `evm` family with network-as-config

ADR-0017 and CONTEXT.md's `Chain` entry established that `Chain` means chain family only (`evm`, `solana`) and that which network an instance talks to — its example: "devnet vs. mainnet-beta, Sepolia vs. Base mainnet" — is deployment config (RPC URL, chain ID, mint/contract addresses), never a separate type-level identity. The `base-chain-handler` research (`.scratch/base-chain-handler/research-base.md`) surfaced why that specific example no longer holds: Base, as an OP-Stack L2, differs from plain Ethereum L1 in ways a config value can't express. It has an L1 data-availability fee computed via the `GasPriceOracle` predeploy (the post-Ecotone blob-fee formula) that plain L1 has no equivalent of at all, and its own confirmation model — sequencer-driven L2 blocks, batched to L1 later — that the decided `CONFIRMED` policy for Base (L2 block inclusion, ~2s, chosen deliberately for speed over waiting for L1 batch inclusion) has no analogue of on L1. These are different fee-computation and status-determination logic, not tuning knobs on one shared code path. So `base` and Ethereum L1 are now separate `Chain` identities, each its own Chain Handler — CONTEXT.md's `Chain` entry is updated to drop the now-wrong "Sepolia vs. Base mainnet" example accordingly.

This does **not** reverse ADR-0017. ADR-0017 killed a *tier* axis (Sandbox/Live, mainnet-vs-testnet) baked into the identifier for multi-tenancy reasons that don't apply here — that holding is untouched: Base mainnet vs. Base Sepolia remain the same `base` Chain, config-only, no separate identity. What's new here is a different axis entirely — execution-layer family (L1 vs. OP-Stack L2) — that ADR-0017 never considered because Base's specific architecture wasn't in view at the time.

## Consequences

Only `base` is being designed/built now (the scratch folder is `base-chain-handler`, not a generic `evm-chain-handler`). Ethereum L1 is an undesigned future feature — whenever it's built, it's its own Chain Handler from scratch, not a config variant added to `base`'s. If low-level EVM-family plumbing that's genuinely identical across both (RLP decoding, secp256k1 recovery, ERC-20 selector encoding) turns out to be worth sharing, that's a separate refactor decision to make once a second real EVM-family Chain Handler actually exists — not speculatively now, per ADR-0012.
