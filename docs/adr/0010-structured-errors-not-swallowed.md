# Errors are structured and surfaced end-to-end, never swallowed into a generic bucket

The reference implementation's coordinator logs the real cause of a failure to the console and reports only a generic `execution_error` to the caller — the actual reason (a revert, a specific RPC failure, a Signer timeout) is thrown away. Every failure mode instead carries a structured shape — `{ code, message, chainDetail? }`, with `code` a small stable set (`INSUFFICIENT_FUNDS`, `INVALID_RECIPIENT`, `SIGNER_UNREACHABLE`, `CHAIN_REJECTED`, `RPC_UNAVAILABLE`, …) — all the way through to the status response and webhook payload. Expected domain outcomes are returned as typed values a caller can branch on directly; exceptions are reserved for truly unexpected failures, not for business-relevant outcomes like "insufficient funds" or "stuck transaction."
