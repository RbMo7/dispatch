# Real Postgres is a third testing tier, not a schema-only static check

ADR-0013 draws two tiers: pure-unit for anything with no I/O, and real infrastructure (no fakes) for exactly the kind of thing that's this project's own hard-won-bug territory — which for Chain Handlers meant real devnet RPC. It never addressed persistence at all: every existing test, including every Coordinator and API-route test, runs `PostgresDispatchStore`'s own interface against `InMemoryDispatchStore` instead, so the real Drizzle schema, its constraints, and its query-builder mapping had zero automated coverage of their own. That gap is exactly what let a real bug hide (core-engine-scaffold issue 14): `transactions.dispatch_id` had a foreign key pointing only at `dispatches.id`, but ADR-0031's `RelayDispatch.transactionId` legitimately points at `relay_dispatches.id` too — every Relay Dispatch broadcast failed its final `INSERT` on a live FK violation, caught only by a manual one-off run against a real local Postgres, never by the automated suite.

A schema-only static check (e.g. asserting Drizzle's schema has no FK pointing at a column that's actually polymorphic) would catch this one bug class, but nothing else `PostgresDispatchStore` could get wrong — a bad column type, a broken migration, a query that doesn't actually express the filter/lock semantics its interface promises (`claimQueued`'s `for('update', skipLocked: true)` is exactly the kind of thing only a real transaction can prove). ADR-0013's own reasoning — real infrastructure catches what a mock/fake/static check can't, and that's worth the cost specifically where a project's differentiating bugs live — applies here just as much as it did to devnet RPC. Persistence is now that third tier: `PostgresDispatchStore`'s own tests run against a real local Postgres, the same schema and migrations a real deployment uses, no fake standing in.

**Provisioning**: the `postgres` service already in `docker-compose.yml` (this repo's existing local-dev Postgres, `postgres://dispatch:dispatch@localhost:5432/dispatch` — `config.databaseUrl`'s own default) is the one instance this tier runs against; no separate docker-compose file or CI-specific provisioning is introduced. There's no CI configured for this repo yet (no `.github/workflows/`), so wiring a Postgres service into CI is deferred until CI itself exists, same as this repo already expects real devnet reachability for `solana-chain-handler`'s own tests with no CI wired up for those either. Migrations (`drizzle-kit migrate`) must be applied to that instance before this tier's tests run, same as any real deployment.

## Consequences

`src/repository/postgres-dispatch-store.test.ts` runs the same way `solana-chain-handler`'s devnet tests do: unconditionally, against real infrastructure, with no skip/gate — a contributor without a reachable, migrated local Postgres will see this tier fail loudly, not silently pass. It truncates its own tables between tests for isolation, since the instance is a shared, persistent local resource, not spun up fresh per run.
